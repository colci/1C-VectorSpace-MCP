# План Универсализации 1C-VectorSpace-MCP

## Цель

Преобразовать проект из MCP-сервера семантического поиска по одной конкретной конфигурации 1С в универсальный инструмент для разработки любых конфигураций 1С на основе выгрузки `XML + BSL`.

Итоговое состояние:

- сервер не привязан к УНФ на уровне кода, индекса и поисковых эвристик
- одна инсталляция может обслуживать одну или несколько конфигураций
- индекс покрывает не только базовые метаданные и BSL, но и формы, команды, подписки, роли и другие важные объекты разработки
- MCP-инструменты поддерживают не только поиск, но и навигацию, impact analysis, usages и call graph
- архитектура допускает optional-интеграции с EDT, BSL LS и справкой платформы 1С

## Главные проблемы текущей версии

### 1. Привязка к УНФ

- дефолтный `EXPORT_PATH` указывает на `D:\Export\UNF`
- имя коллекции Qdrant формируется как `1c_unf_configuration_*`
- часть semantic lookup эвристик ориентирована на бизнес-термины УНФ
- документация все еще описывает проект как решение для УНФ

### 2. Недостаточное покрытие сущностей разработки

- индексируются только BSL и часть XML-метаданных
- формы и шаблоны сейчас исключаются из индексации
- отсутствуют отдельные чанки для команд, подписок на события, ролей, общих форм, макетов и смежных объектов

### 3. Слабая модель связей

- `get_dependencies` строится по текстовой карточке, а не по нормализованному графу зависимостей
- нет `where_used`
- нет call graph между методами
- нет связей форма -> команда -> обработчик -> модуль

### 4. Недостаточная универсальность для ежедневной разработки

- нет поиска по модулям и формам как отдельным сущностям
- нет целевого reindex по файлу/пути/конфигурации
- нет объяснения ранжирования результатов
- нет слоя справки платформы 1С
- нет optional live-интеграции с EDT или BSL LS

## Архитектурное направление

Проект стоит развивать в три слоя.

### Слой 1. Universal Export Index

Основа системы:

- загрузка выгрузки любой конфигурации 1С
- нормализация и чанкинг `XML + BSL`
- построение эмбеддингов и payload-индексов
- хранение в Qdrant

### Слой 2. Graph-Light Navigation

Навигационный слой:

- зависимости между объектами метаданных
- usages объектов и методов
- callers/callees
- связи модуль/форма/команда/обработчик

### Слой 3. Optional Dev Integrations

Расширения, не обязательные для базовой работы:

- справка платформы 1С
- BSL Language Server
- EDT
- runtime/toolkit доступ к базе

## Этап 3A. Переход от JSON Graph Cache к Memgraph

### Цель

Перевести проект от чтения графа из большого локального JSON-файла к архитектуре с абстракцией графового backend и shared graph storage на базе Memgraph.

### Ключевые архитектурные решения

- ввести слой `GraphRepository`, чтобы `mcp_server.py` не знал, откуда пришел граф: из JSON или из графовой БД
- зафиксировать целевую модель графа:
  - `MetadataObject`
  - `Form`
  - `Module`
  - `Method`
  - позже: `Command`, `Handler`
- зафиксировать типы ребер:
  - `REFERENCES`
  - `CONTAINS_FORM`
  - `CONTAINS_MODULE`
  - `DECLARES_METHOD`
  - позже: `CALLS`, `USES`, `HANDLES_COMMAND`
- переписать `build_graph_cache()` в режим `build_graph_projection()`, где результат можно отправить и в JSON, и в графовую БД

### Переходная модель

- на первом этапе оставить `dual-write`
- индексатор строит граф и пишет его и в JSON, и в Memgraph
- read-инструменты переводить постепенно:
  - сначала `get_dependencies`, `list_object_forms`
  - затем `find_method`, `find_usages`, `get_callers`, `get_callees`
- после стабилизации убрать JSON как primary source и оставить его только как fallback/debug artifact

### Ops-слой

Отдельно нужно добавить инфраструктурный слой:

- `Docker Compose`
- `healthcheck`
- `backup job`
- `reload/reindex pipeline`
- `smoke tests` на Cypher-запросы

### Этапы внедрения

### Этап 1, 1-2 недели

- поднять Memgraph в Docker
- добавить `GraphRepository`
- реализовать загрузку узлов и ребер в Memgraph
- перевести `get_dependencies` и `list_object_forms`

### Этап 2, 1-2 недели

- добавить `CALLS` и `USES`
- реализовать `find_usages`, `get_callers`, `get_callees`
- сравнить результаты `JSON vs DB` на regression cases

### Этап 3

- убрать загрузку `graph_cache_default.json` в память процесса
- оставить JSON только как `export/debug snapshot`
- добавить `backup` и процедуру `reindex`

### Что важно не пропустить

- не переносить в граф все подряд
- в Qdrant должен оставаться семантический поиск
- в графовой БД должны жить только структурная навигация и связи
- не превращать графовую БД во "второй Qdrant"
- сразу нормализовать идентификаторы узлов, чтобы они были стабильны между переиндексациями

### Критерий готовности

- `mcp_server.py` работает через `GraphRepository`, а не против конкретного JSON-файла
- индексатор умеет `dual-write` в JSON и Memgraph
- `get_dependencies` и `list_object_forms` уже работают через графовую БД
- JSON перестает быть primary source и остается только как fallback/debug слой
- для Memgraph есть базовый ops-контур: контейнер, healthcheck, backup и reindex

## Этап 3B. Переход на полноценный AST-анализатор BSL

### Цель

Уйти от regex/heuristic-парсинга BSL как от временной меры и сделать AST-анализатор основным источником структурных связей по коду.

### Зачем это нужно

- уменьшить ложные срабатывания в `CALLS` и `USES`
- корректно разбирать квалифицированные вызовы, локальные переменные, параметры и контекст модуля
- подготовить базу для `find_usages`, `get_callers`, `get_callees`, `HANDLES_COMMAND` и последующего impact analysis
- сделать результаты стабильными между переиндексациями и изменениями стиля кода

### Целевая модель

- AST-анализатор строит нормализованное представление:
  - declarations
  - call sites
  - metadata usages
  - command handlers
  - module context
- именно AST-слой становится источником для генерации ребер:
  - `CALLS`
  - `USES`
  - позже `HANDLES_COMMAND`
- текущие regex/heuristic-правила остаются только как bootstrap/fallback режим до полной стабилизации AST-контура

### Изменения в архитектуре

### [index_config.py](/D:/work/1C-VectorSpace-MCP/index_config.py:1)

- выделить отдельный этап `BSL analysis pipeline`
- отделить `parse_bsl_source()` от логики построения graph projection
- перевести `extract_call_candidates()` и `extract_metadata_usages_from_bsl()` в fallback-слой
- собирать `CALLS` и `USES` сначала из AST, а heuristics использовать только там, где AST еще не покрывает кейс

### [mcp_server.py](/D:/work/1C-VectorSpace-MCP/mcp_server.py:1)

- не менять контракт MCP-инструментов
- перевести `find_usages`, `get_callers`, `get_callees` на более точные AST-derived связи без изменения внешнего API

### Этапы внедрения

### Этап 1, 1-2 недели

- выбрать и интегрировать полноценный AST-анализатор BSL
- зафиксировать промежуточный internal format для `MethodDecl`, `CallSite`, `MetadataUsage`, `CommandHandler`
- подключить AST-разбор хотя бы для `CommonModule`, `ObjectModule`, `ManagerModule`, `FormModule`

### Этап 2, 1-2 недели

- начать строить `CALLS` и `USES` из AST как primary source
- оставить heuristics как fallback для неподдержанных конструкций
- добавить regression-набор кейсов: прямые вызовы, квалифицированные вызовы, экспортные методы, формы, команды, обработчики

### Этап 3

- отключить heuristics как основной источник
- оставить regex-ветку только как debug/fallback режим
- расширить AST-контур на команды, обработчики и сложные сценарии разрешения вызовов

### Что важно не пропустить

- AST-анализатор не должен смешиваться с семантическим поиском; это слой структурного понимания кода
- stable node ids и method ids должны сохраняться независимо от конкретного парсера
- нужно сравнивать `heuristics vs AST` на контрольном наборе выгрузок перед отключением старого контура
- AST-слой должен быть встроен в `build_graph_projection()`, а не жить отдельной несвязанной утилитой

### Критерий готовности

- `CALLS` и `USES` строятся преимущественно из AST
- `find_usages`, `get_callers`, `get_callees` показывают меньше ложных связей на regression-наборе
- heuristics перестают быть основным механизмом анализа BSL и остаются только как fallback/debug слой
