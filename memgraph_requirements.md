# Требования К Memgraph Для Командного Использования

Обновлено: 2026-07-02

## Назначение

Этот документ фиксирует практические требования к Memgraph для использования проекта как общего графового backend-сервиса для команды из 4 разработчиков, работающих с 1С MCP-сервисом.

Цель Memgraph в этом проекте не в замене Qdrant и не в хранении полных текстов кода. Memgraph планируется использовать как структурное графовое хранилище для навигации, зависимостей, поиска использований и обхода вызовов.

## Исходные Допущения Проекта

- Размер команды: 4 разработчика
- Модель использования: общий read-mostly сервис
- Основной backend семантического поиска остается Qdrant
- Memgraph хранит только структуру графа
- Полные тексты кода, карточки метаданных и длинные документы должны оставаться в Qdrant и/или в файлах

## Текущая Базовая Оценка Графа

По текущему handoff проекта:

- Узлов: 202,829
- Связей: 200,413
- Основные типы узлов: `metadata`, `form`, `module`, `method`
- Текущий источник графа: `graph_cache_default.json`

Эти значения принимаются как базовая точка для первоначального sizing и могут вырасти после добавления связей `CALLS`, `USES`, обработчиков команд и других графовых отношений.

## Рекомендуемая Роль Memgraph

Memgraph должен хранить только структурные сущности и связи:

- Узлы:
  - `MetadataObject`
  - `Form`
  - `Module`
  - `Method`
- Связи:
  - `REFERENCES`
  - `CONTAINS_FORM`
  - `CONTAINS_MODULE`
  - `DECLARES_METHOD`
  - в дальнейшем: `CALLS`, `USES`, `HANDLES_COMMAND`

## Что Нужно Хранить В Memgraph

Рекомендуемые свойства узлов:

- стабильный `id`
- `kind`
- `config_id`
- `object_type`
- `object_name`
- `module_path`
- `module_type`
- `method_name`
- `file_path`
- `start_line`
- `end_line`
- небольшие технические флаги, нужные для MCP-запросов

Рекомендуемые свойства связей:

- `type`
- `section`
- `container`
- `source`
- легковесные технические атрибуты, нужные для обхода и объяснения результата

## Что Не Следует Хранить В Memgraph

Не нужно хранить большие текстовые payload как основное содержимое графа:

- полные тексты BSL-методов
- полные карточки метаданных
- большие описания форм
- дубли документов для семантического поиска, которые уже лежат в Qdrant

Причины:

- Memgraph в основном работает как in-memory база
- большие текстовые свойства резко увеличат расход RAM
- Qdrant уже лучше подходит для семантического retrieval

## Требования По Ресурсам Для 4 Пользователей

### 1. Минимум Для Пилота

Использовать только для тестов и ранней валидации:

- CPU: 2 vCPU
- RAM: 4 GB
- Disk: 20-30 GB SSD

### 2. Комфортная Базовая Конфигурация Для Команды

Рекомендуемая стартовая production-конфигурация для 4 разработчиков, если Memgraph хранит только структурный граф:

- CPU: 4 vCPU
- RAM: 8 GB
- Disk: 50 GB SSD

Это предпочтительная стартовая конфигурация для проекта.

### 3. Более Безопасный Production-Запас

Рекомендуется, если сервис используется постоянно, граф растет и добавляются новые инструменты обхода:

- CPU: 4-8 vCPU
- RAM: 16 GB
- Disk: 100 GB SSD

### 4. Если Memgraph И Qdrant Живут На Одном Хосте

Если оба сервиса работают на одной машине:

- RAM хоста следует планировать от 32 GB
- SSD следует планировать от 100 GB

Это дает запас для:

- in-memory графа Memgraph
- векторов и индексов Qdrant
- переиндексации
- WAL и snapshots
- конкурентных MCP-запросов

## Логика Оценки Ресурсов

Документация Memgraph указывает, что ключевой ресурс для sizing это RAM, и дает упрощенную формулу оценки графа:

- память на узел: около 128 байт на узел
- память на связь: около 120 байт на связь

Упрощенное правило:

`128 * N + 120 * R`

Затем отдельно нужно добавить:

- overhead на свойства
- overhead на индексы
- память на выполнение запросов

Для обычных графовых запросов без тяжелых алгоритмов стоит закладывать примерно `1.5x` поверх оценки at-rest графа.

Для этого проекта формула полезна только как базовая оценка. Реальное потребление памяти в первую очередь будет зависеть от того, попадут ли в граф большие текстовые свойства.

## Замечания По Надежности И Диску

Memgraph использует WAL и snapshots для durability. Поэтому диск должен учитывать не только "живую" базу, но и:

- активные файлы базы
- WAL-файлы
- snapshots
- резервные копии

Из-за этого disk planning нельзя строить только по размеру актуального графа.

## Операционные Рекомендации

Для первого внедрения Memgraph:

1. Сохранить Qdrant как backend семантического поиска.
2. Использовать Memgraph только для структурного обхода и детерминированной графовой навигации.
3. Оставить один indexing pipeline как единственный writer.
4. Подключать Memgraph к MCP как общий read-mostly сервис.
5. Добавить healthcheck, backup и процедуру reindex до командного rollout.

## Итоговая Рекомендация

Для этого проекта и команды из 4 разработчиков рекомендуемая первая конфигурация такая:

- роль Memgraph: только структурный граф
- сервер: 4 vCPU / 8 GB RAM / 50 GB SSD
- если Memgraph и Qdrant живут вместе: хост от 32 GB RAM

Если граф начнет хранить большие текстовые payload или сервис станет более тяжелой общей платформой, переходить на:

- 4-8 vCPU / 16 GB RAM / 100 GB SSD
